# 外部定时器：Cloudflare Worker Cron

> 目标：每天北京时间 **15:30** 稳定触发 GitHub Actions 的 `daily-vp` 收盘任务，不再依赖 GitHub 自身的 `schedule`。

## 为什么需要它

GitHub Actions 的 `schedule` 是尽力而为：

- 可能延迟几十分钟到几小时；
- 高负载时可能丢弃排队任务；
- 新仓库/新 workflow 前几天更不稳定。

Cloudflare Worker Cron 负责“准点按门铃”，GitHub Actions 仍然负责真正的生成、提交和部署。

## 架构

```text
Cloudflare Cron（07:30 UTC = 15:30 CST）
        │
        ▼
worker/index.mjs scheduled()
        │ POST GitHub API
        ▼
GitHub Actions workflow_dispatch
  workflow: daily.yml
  ref: main
  inputs: session=close
        │
        ▼
publish（生成/提交） → deploy（Cloudflare 部署 + 线上校验）
```

保留 GitHub 的 18:20 收盘兜底：如果 15:30 没成功，18:20 再试；如果已经成功，18:20 检测到当天 `close` 已存在会跳过。

## 前置条件

- Cloudflare 账号：已有 `ashare-vp` Worker
- GitHub 仓库：`lx7575000/ashare-vp`
- 本机/CI 能执行 `wrangler deploy`
- 一个 GitHub Fine-grained PAT

## 1. 创建 GitHub Token

GitHub → **Settings → Developer settings → Fine-grained tokens → Generate new token**：

- Repository access：只选 `lx7575000/ashare-vp`
- Permissions：
  - **Actions: Read and write**
  - **Metadata: Read-only**
- 有效期建议 90 天，到期前轮换

复制 token，只显示一次。

## 2. 在 Cloudflare 配置 Secret

Cloudflare Dashboard → **Workers & Pages → ashare-vp → Settings → Variables and Secrets**：

- Name：`GITHUB_TOKEN`
- Value：上一步的 token
- 类型：**Secret / Encrypt**

或者本地执行：

```bash
npx wrangler secret put GITHUB_TOKEN
```

不要把 token 写进 `wrangler.jsonc`、Git 或聊天记录。

## 3. 部署 Worker

`wrangler.jsonc` 已经配置：

- `main: worker/index.mjs`
- `assets.binding: ASSETS`
- `triggers.crons: ["30 7 * * 1-5"]`

第一次部署可以手动跑一次 `daily-vp`：

1. GitHub → Actions → daily-vp → Run workflow
2. `session` 选 `close`
3. `force` 不勾
4. Run

这个 run 的 `deploy` job 会执行 `wrangler deploy`，同时把 Worker 代码、静态资源和 Cron Trigger 部署上去。

> 注意：`wrangler deploy` 必须先有 `GITHUB_TOKEN` Secret，否则 Worker 部署成功但 Cron 触发时会报错。

本地也可以：

```bash
npx wrangler deploy
```

## 4. 验证

### 4.1 Cloudflare 侧

Dashboard → **Workers & Pages → ashare-vp → Triggers**，确认：

```text
30 7 * * 1-5
```

这是 UTC，对应北京时间 **15:30**。

### 4.2 本地测试 scheduled

安装依赖并启动：

```bash
npx wrangler dev --test-scheduled
```

另开终端触发一次：

```bash
curl "http://localhost:8787/__scheduled?cron=30+7+*+*+1-5"
```

本地需要能读到 `GITHUB_TOKEN`（可用 `.dev.vars`，不要提交）。

成功后：

- Worker 控制台打印 `cron triggered: 30 7 * * 1-5`
- 打印 `dispatched lx7575000/ashare-vp daily.yml@main session=close`
- GitHub Actions 出现一条 `workflow_dispatch` 运行

### 4.3 静态站点不能坏

部署后检查：

```bash
curl -I https://ashare-vp.narcissusliu0428.workers.dev/
curl -I https://ashare-vp.narcissusliu0428.workers.dev/history
curl -I https://ashare-vp.narcissusliu0428.workers.dev/data/latest.json
```

都应返回 200。Worker 的 `fetch()` 会把请求交给 `env.ASSETS.fetch(request)`。

### 4.4 线上验收

15:30 之后检查：

```text
https://ashare-vp.narcissusliu0428.workers.dev/data/latest.json
```

应满足：

- `meta.as_of` = 当天
- `meta.session` = `close`
- `meta.replay` = `false`
- `meta.generated_at` 在 15:30 左右
- `assets` 数量 ≥ 20

GitHub Actions 应出现：

```text
event: workflow_dispatch
session: close
```

并生成：

```text
site: YYYY-MM-DD close
```

18:20 的兜底应显示 skipped，或检测到当天 `close` 已存在而跳过。

## 5. 监控与失败处理

- **Cloudflare 日志**：Dashboard → Worker → Logs，或 `npx wrangler tail`
- **GitHub Actions**：失败会发邮件；手动 Run workflow 可补跑
- **Worker 失败**：`scheduled` 会抛错，Cloudflare 日志能看到 HTTP 状态和响应体
- **Token 过期**：Worker 日志会出现 401；重新生成 token 并更新 Secret

如果希望失败时主动通知，可以在 `scheduled` 的 catch 里加 webhook（Discord/飞书/邮件 API），但不建议阻塞主流程。

## 6. 回滚

如果 Worker 方式出问题，可以回滚：

1. 从 `wrangler.jsonc` 删除 `main`、`assets.binding`、`triggers`
2. 删除 `worker/index.mjs`（或保留但不再引用）
3. 重新部署

或者临时把 15:30 的 GitHub `schedule` 加回来：

```yaml
- cron: "30 7 * * 1-5"
```

并保留 18:20 兜底。

## 7. 注意事项

- Cloudflare Cron 使用 **UTC**，不是北京时间；`30 7 * * 1-5` 才是 15:30 CST。
- 中国不实行夏令时，全年固定 UTC+8。
- `workflow_dispatch` 的 `inputs` 都是字符串；`session` 传 `close` 即可，`force` 不传默认为 `false`。
- Worker 只负责触发，不生成报告；报告仍由 GitHub Actions 里的 Python 生成。
- 公开仓库的 Actions 免费；Cloudflare Cron 每天 1 次，免费额度足够。
- Token 最小权限：只给 `Actions: Write` 和 `Metadata: Read`，不要给全仓库写权限。
