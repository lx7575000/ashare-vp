
### 3.3 创建 Cloudflare API Token

1. 打开 [API Tokens](https://dash.cloudflare.com/profile/api-tokens) → **Create Token**
2. 选 **Edit Cloudflare Workers** 模板（最省事），或自定义：
   - `Account` → `Workers Scripts` → `Edit`
3. 创建后复制 Token（只显示一次）
4. Account ID：**Workers & Pages** 页面右侧，或 dashboard URL 里的 `dash.cloudflare.com/<account_id>`

> 注意：Worker 用 `Workers Scripts:Edit`，不是 `Cloudflare Pages:Edit`；Token 必须属于创建 `ashare-vp` 的那个 Cloudflare 账号，否则会部署到另一个账号。

### 3.4 在 GitHub 加 Secrets

仓库 → **Settings** → **Secrets and variables** → **Actions** → **New repository secret**：

| Name | Value |
|---|---|
| `CLOUDFLARE_API_TOKEN` | 上一步的 Token（如需自动清缓存，再给它 `Zone.Cache Purge` 权限） |
| `CLOUDFLARE_ACCOUNT_ID` | 你的 Account ID |
| `CLOUDFLARE_ZONE_ID` | 可选；用于部署后清理缓存。没有就跳过清理，依赖 `wrangler deploy` 的版本切换和线上校验 |

### 3.5 确认 workflow

[`.github/workflows/daily.yml`](../.github/workflows/daily.yml) 已经写好：

- 定时（UTC）：
  - `30 2 * * 1-5` = **10:30 北京时间**
  - `0 6 * * 1-5` = **14:00 北京时间**
  - `20 10 * * 1-5` = **18:20 北京时间（收盘）**

- 部署配置：[`wrangler.jsonc`](../wrangler.jsonc)，Worker 名 `ashare-vp`，静态目录 `./site`

## 4. 关键细节

### 4.1 时区

- cron 用 UTC：`30 2 * * 1-5` = 10:30 CST，`0 6 * * 1-5` = 14:00 CST，`20 10 * * 1-5` = 18:20 CST
- workflow 设置 `TZ=Asia/Shanghai`，`date +%F` 和报告日期都按北京时间
- 10:30 / 14:00 用 `ashare_vp.session --require-current`；收盘用 `ashare_vp`，再由 `build_site.py --require-date` 兜底

### 4.2 节假日

- 盘中（10:30 / 14:00）：`--require-current` 没有当日实时快照时退出码 3，workflow 直接跳过；
- 收盘：`build_site.py --require-date "$(date +%F)"` 检查 `as_of`，不是今天就退出码 3，跳过提交和部署；
- 时段窗口：workflow 在生成前还会检查北京时间，10:30 只允许 10:15–11:20、14:00 只允许 13:45–14:50、收盘只允许 15:05 之后；手动 dispatch 勾选 `force` 可忽略窗口做回放；
- 行情源还没更新 → 同样跳过；可手动 Run workflow 补跑。

### 4.3 数据源异常

- 工具内置腾讯 → 新浪 → 东财容错，单只失败不影响整体
- `--min-assets 20`：少于 20 个标的拒绝发布
- 同一天重复运行，如果新报告比已有归档少标的，`build_site.py` 会保留更完整的旧归档
- workflow 用 `actions/cache` 恢复 `data/snapshots`，保证 14:00 能对比 10:30、收盘能对比 14:00；缓存不占 Git 仓库
- 生成失败 → Action 红叉 + GitHub 邮件；修复后手动重跑

### 4.4 历史与体积

- 每期约 170 KB，每天最多 3 期（10:30 / 14:00 / 收盘）
- 保留 120 天，站点约 50–60 MB，Git 压缩后更小；如在意体积可把 `--prune-days` 改成 90
- 只提交 `site/`；原始报告、快照、行情缓存都不入库

### 4.5 脱敏与访问

- `build_site.py` 会把 `/Users/<你>/...` 替换为相对路径；部署前可 `grep -r "/Users/" site`
- 页面带 `noindex,nofollow` 和 `robots.txt`，不会被搜索引擎收录
- 页面是“知道 URL 就能访问”；需要登录可加 Cloudflare Access（手机多一步验证码）
- Token 只放 GitHub Secrets，不要写进代码

### 4.6 缓存

Worker 对 HTML 返回 `cache-control: public, max-age=0, must-revalidate`，刷新即可看到最新；如果手机浏览器缓存旧页，加 `?v=日期` 强制刷新。

## 8. 优化路线与 Wind API 方案

### 8.1 先说结论

数据源和工具能减少错误，但不能保证“更准”。这套日报的改进优先级建议是：

1. 先保证**按时、不断更、可回看**（已完成三时段自动化）；
2. 再补**交易日历、数据校验、分钟线、复权、交易成本/回测**；
3. 最后才考虑 **Wind** 这类重型数据源。

### 8.2 优先级清单

| 优先级 | 改进 | 解决什么问题 | 代价 |
|---|---|---|---|
| P0 | 交易日历 | 节假日误跑/空跑 | 低 |
| P0 | 数据质量校验 | 缺标的、旧数据、字段异常 | 低 |
| P1 | 分钟线/成交量分布 | 10:30 / 14:00 的量比线性外推误差 | 中 |
| P1 | 基准相对强弱/行业中性 | 单看个股信号噪音大 | 中 |
| P1 | 回测 + 交易成本 | 验证信号是否真有边际 | 中 |
| P2 | Wind 数据源 | 复权、停牌、成分股、实时行情 | 高（终端/授权/本机） |
| P2 | 飞书/微信推送 | 主动知道报告已更新 | 低 |

### 8.3 Wind API 怎么接（方案先行）

WindPy 的现实约束：

- 需要 Wind 终端 + 授权账号，**通常绑定 Windows 机器**；
- GitHub Actions 云端跑不了（没有终端、没有授权）；
- 实时 `wsq` / 历史 `wsd` 都依赖本机终端；
- **授权提醒**：Wind 数据对外公开可能受许可限制。若要公开站点，优先用公开源；Wind 更适合内部校验，或给站点加访问控制。

三种接法：

| 模式 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. Wind 本机全量** | 本机 10:30 / 14:00 / 18:20 跑 `--source wind`，生成 `site/` 后 `wrangler deploy` | 三个时段都用 Wind | 机器必须常开 |
| **B. 混合（推荐）** | 云端免费源跑 10:30 / 14:00；18:20 本机 Wind 跑收盘并覆盖 | 盘中不依赖本机，收盘用高质量数据 | 两套数据源口径要统一 |
| **C. 仅校验** | 云端照常跑；本机 Wind 每天生成“数据核对/复权校准”报告 | 改动最小 | 不提升盘中数据 |

代码层怎么接：

- 新增 `providers/`：`WindProvider` 实现与腾讯/新浪相同的 `fetch_bars` / `fetch_quote` 接口；
- 命令行加 `--source wind`，配置加 `source_order: ["wind", "tencent", ...]`；
- 统一 `Bar` / `Quote` 字段：`date/open/high/low/close/volume/amount/turnover/adj_factor`；
- 报告 `meta` 增加 `data_source`、`adjust`、`stale`、`calendar`；
- Wind 不可用时自动回退腾讯/新浪，报告标注来源；
- 测试用固定样本 mock WindPy，不依赖终端。
